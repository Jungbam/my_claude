# QA 검증 원칙 (SSOT) [L2]

> 온디맨드 문서. QA 리포트를 쓰거나 QA 판정을 내리기 전에 Read한다.
> 참조처: 탐색형 QA(`/bams:qa`, `qa`·`qa-only` 엔진), 감사형 QA(`/bams:qa --audit`, `qa-audit` 엔진), `design-qa`, QA부 에이전트(qa-strategy·automation-qa·defect-triage·release-quality-gate).

심각도·증거 등급·게이트 임계값은 이 문서가 정의하지 않는다 — `references/issue-severity.md`가 SSOT다. 이 문서는 "무엇을 어떻게 관찰하고 어떻게 적는가"만 다룬다. 리포트는 각 원칙을 지켰는지 스스로 밝힌다.

## 1. 검증 원칙 8

| # | 원칙 | 리포트에서 지키는 방법 | 범용 예시 |
|---|---|---|---|
| 1 | 분모를 밝힌다. 전수가 기본, 표본이면 표본이라고 쓴다 | `대상 N개 × viewport K = 방문 V회`, 미방문·미확인 수를 0이라도 쓴다 (§5) | 상품 상세 120개 × 2 viewport(1440×900·390×844) = 방문 240회, 미방문 0 |
| 2 | 지어내지 않는다 | 원천에 없는 값·단위·배율은 `확인 필요`로 남긴다. 하위 값을 다시 더하거나 임의로 배분하지 않는다 | 단위 표기 없는 금액 `52.7`을 "억 원"으로 추정해 판정하지 않음. 지역 합계를 하위 지역 값으로 재합산하지 않음 |
| 3 | 0 / 미표기(—) / 데이터 부재는 다른 상태다 — 화면·보조기기 모두 | 세 상태를 따로 세고, 화면 표시와 스크린 리더 낭독이 각각 구분되는지 확인한다 | 재고 `0` / 재고 `—`(미표기) / 재고 데이터 없음이 같은 "0"으로 보이거나 같은 문장으로 읽히면 결함 후보 |
| 4 | 측정 조건을 쓰고, 측정값을 보장으로 해석하지 않는다. dev 서버 성능 수치를 운영 수치로 쓰지 않는다 | 서버 종류(dev / prod build / staging), 캐시 상태, viewport, 관찰 시간을 표 위에 쓴다 | dev 서버·캐시 공유·load 후 5초 관찰의 CLS 표본은 운영 성능도, 개선율도 아니다 |
| 5 | 실패 기록을 보존하고 최종 결과와 분리한다 | 원시 결과(`*.jsonl`)는 모든 시도를 남기고, 요약은 최신 시도 + 재시도 수로 쓴다 | 상류 502가 재시도로 복구된 건은 별도 기록. 외부 이미지 404는 기능 결함과 분리 |
| 6 | 못 한 검증은 미검증이라고 쓴다 | `미검증·한계` 절을 생략하지 않는다. 미검증 범위는 `unverified`로 표기 (§8) | 로그인 세션 없음, 외부 API 키 미설정으로 일부 화면 503 → 한계로 명시 |
| 7 | 관찰만 한다 — 수정은 사용자 요청 시 `/bams:hotfix`·`/bams:dev`로 | 지연·오류 주입은 QA 브라우저 안에서만 한다. 대상 레포 코드·env·DB를 바꾸지 않는다 | 로딩 상태 확인용 응답 지연은 브라우저 요청 가로채기로만 주입, 서버 코드·env 미변경 |
| 8 | 실제 UI를 도구에 맞추지 않는다. 자동 검사 통과 ≠ 준수 | "위반 0"은 `자동 검사 위반 0`으로 쓴다. 4xx/5xx 화면은 정상 UI 검사로 세지 않는다 | 500 오류 화면의 자동 접근성 검사 결과를 정상 화면 집계에서 제외. 스켈레톤에 맞춰 실제 UI를 바꾸지 않음 |

## 2. 리포트 문장 규칙

- 숫자에는 분모와 조건을 붙인다: "16개 표본(8 경로 × 2 viewport)의 CLS는 0–0.01 (dev 서버, load 후 5초)".
- "검증 완료", "문제 없음"은 실행한 범위에만 쓴다. 범위 밖은 "미검증"이다.
- 스크립트 후보와 확인된 결함을 섞지 않는다: "후보 30건 중 코드 확인 결과 결함 9건, 의도된 예외 21건".
- 이전 리포트의 결론을 현재 사실로 재사용하지 않는다. 다시 실행했거나, 실행하지 않았다고 쓴다.
- 코드가 바뀌면 이전 결과는 근거가 아니다. 변경 이후 재실행한 결과만 근거로 쓴다.
- "많다"·"자주"·"대부분" 대신 실측 건수로 쓴다: "목록이 많다" → "한 화면 최대 N건, 중앙값 M건".
- 방향 선택이 필요한 지적(공용 부품 변경, 여러 해법이 가능한 UX 문제)은 증상·원인과 함께 **선택지 2~3개**를 준다. 하나만 제시하면 결정 요청이 아니라 통보다.
- 실측으로 뒤집힌 판단은 지우지 않고 **정정 과정**(처음 판단 → 측정 → 바뀐 판단)을 남긴다.
- 검증 게이트(프로젝트 검증 명령·감사 스크립트)는 **직렬**로 실행한다 — 출력이 섞이면 어느 게이트가 실패했는지 짚을 수 없다. 리뷰 반영 등으로 코드가 바뀌면 일부가 아니라 **전부** 다시 실행한다.

## 3. 증거 층위

| 층위 | 내용 | 결함으로 셀 수 있나 |
|---|---|---|
| 스크립트 결과 | 정적 스캔·computed style·자동 접근성 검사·측정 스크립트의 결정론적 출력 | 아니오 — **후보**. 코드(`file:line`) 또는 화면으로 확인한 뒤에만 결함 |
| LLM 판정 | 스크린샷·DOM·문맥을 읽고 내린 해석 | 후보를 확인하거나 기각하는 근거. 단독으로는 재현 증거가 아님 |
| 확인 결함 | 재현 단계 + 증거(스크린샷·명령 출력·`file:line`)가 붙은 항목 | 예 — 심각도 집계 대상 |

증거 등급 대응 (등급 정의는 `references/issue-severity.md` §증거 등급, 여기서 재정의하지 않는다):

- 브라우저·스크립트로 직접 관찰 → `measured`
- 실행하지 않고 코드 경로 추적으로 도출 → `inferred`
- 재현 경로 없는 추정 → `guess` — 결함으로 확정하지 않는다(허용 심각도 범위에서 기록만)
- 확인 못 한 후보는 결함 집계에 넣지 않는다. 확인 못 한 P0(critical) 후보는 `unverified-risk` (§8)

## 4. 대상 레포 제약 선행 확인

QA 시작 전에 대상 레포의 `CLAUDE.md`, `.crew/config.md`, `.crew/gotchas.md`를 먼저 읽는다(없으면 건너뜀).

- 금지 작업 예: 자동 커밋·stash, 테스트 프레임워크 추가, build 실행, DB 쓰기, 새 env 추가.
- 금지 작업이 QA 단계(수정 루프의 원자 커밋, clean tree 요구, 테스트 부트스트랩 등)와 충돌하면 **그 단계를 건너뛰고** 리포트 `미검증·한계`에 "제약으로 건너뜀: {단계} — {제약 출처}"를 기록한다.
- 대상 레포 제약을 QA 편의로 덮어쓰지 않는다. 제약 목록은 위임 메시지·실행 지시에 첨부한다.

## 5. 분모

| 모드 | 리포트에 쓰는 분모 |
|---|---|
| 탐색 | `발견 D / 방문 V / viewport K / 미방문 사유` (발견했지만 방문하지 않은 페이지는 사유를 적는다) |
| diff-aware | `영향 라우트 R 중 T 검증` (미검증 R−T개는 `unverified`) |
| 감사 | 축별 `대상 N × viewport K = 측정 V회`, 측정 실패·건너뜀 수 |

분모가 0이거나 비어 있으면 "검사 대상 없음"이지 "문제 없음"이 아니다.

**화면이 다루는 데이터 규모를 먼저 잰다.** 화면만 보면 규모를 모른다. 목록·표·선택 목록마다 실제 데이터의 최대 건수와 중앙값을 먼저 재서 범위 표에 쓴다. 페이지당 건수, 검색형 선택, 가상화, 빈 상태 같은 판단은 이 수치를 근거로 한다. 잴 수 없으면 `미검증`으로 쓴다.

## 6. 산출물 경로

| 항목 | 경로 |
|---|---|
| 실행 단위 `<run>` | `.crew/artifacts/qa/{YYYY-MM-DD}-{scope}[-n]/` (scope = `explore-{domain}` 또는 `audit-{axes}`) |
| 리포트 | `<run>/report.md` — 첫 줄 판정 줄 |
| 원시 증거 | `<run>/*.json\|jsonl\|md`, `<run>/screens/*.png`, `<run>/gallery.html` |
| 회귀 기준 | `<run>/baseline.json`. `--regression` 기본 = 최신 `.crew/artifacts/qa/*/baseline.json` |
| 테스트 계획 입력 | `~/.gstack/projects/$SLUG/*-test-plan-*.md` **읽기 유지** (plan-eng-review·autoplan이 씀) |
| 폐기 | `~/.gstack/projects/{slug}/…-test-outcome-…md` 쓰기 (소비자 0) |
| 프로젝트 프로필 | 대상 레포 `.crew/qa-profile.json` + `.crew/qa-profile.md`(선택) |
| 의도 원장·놓친 결함 | 대상 레포 `.crew/qa-intent-ledger.md` |
| 디자인 파이프라인 a11y | 기존 `.crew/artifacts/design/{slug}/a11y/` 유지(`--out`만) |

- `--regression`에서 예전 `.gstack/qa-reports/baseline.json`은 사용자가 경로를 명시했을 때만 읽는다.
- 프로필·원장 파일이 없으면 기본값으로 진행한다.

## 7. 판정 연결

QA 심각도(탐색 critical/high/medium·low, 감사 P0/P1/P2)와 게이트 판정은 `references/issue-severity.md` §QA 판정 매핑을 따른다. health score는 참고 지표이며 게이트가 아니다.

## 8. 용어

| 용어 | 의미 | 정의 위치 |
|---|---|---|
| 미검증 = `unverified` | 실행하지 못했거나 증거가 없는 범위·지적. 결함 집계에서 제외 | `references/issue-severity.md` §증거 등급 |
| `unverified-risk` | 확인 못 한 고위험 후보(QA에서는 확인 못 한 P0 후보). 건수에 넣지 않지만 PASS 불가 | `references/issue-severity.md` §증거 등급 |
| 증거 등급 (`measured`·`inferred`·`guess`) | 지적의 증거 수준과 허용 심각도 | `references/issue-severity.md` §증거 등급 |
| 후보 | 스크립트·자동 검사 결과 중 아직 확인하지 않은 항목. 결함 아님 | 이 문서 §3 |
| 핵심 경로 | 정의·게이트 효과: `references/issue-severity.md` §QA 판정 매핑 | `references/issue-severity.md` §QA 판정 매핑 |
